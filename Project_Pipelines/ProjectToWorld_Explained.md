## 问题 1：我们是怎么反投影到 3D 的？

### 针孔相机模型（原理）

LiDAR 给你一张 2D 图，每个像素有一个深度值 `d`。要还原成 3D，需要"逆推"光线方向：

```
                    真实世界中的点 P
                         *
                        /
                       / 距离 = d
                      /
       ─────────────●───────────── 图像平面（深度图）
                   (bx, by) ← 像素坐标
                    |
                    | 焦距 f
                    |
                    ● 相机中心
```

**正向**（拍照）：3D 点 → 除以深度 → 2D 像素  
**反向**（我们做的）：2D 像素 × 深度 → 3D 点

### 数学公式（两步）

**第一步：像素坐标 → 相机坐标系中的 3D 点**

```
x_cam =  d × (bx - cx) / fx
y_cam = -d × (by - cy) / fy    ← 负号因为图像 Y 向下，相机 Y 向上
z_cam = -d                       ← 负号因为相机朝 -Z 看
```

其中：
- `(bx, by)` = 深度图上的像素位置
- `(cx, cy)` = 图像中心点（主点）— Apple 标定好的
- `(fx, fy)` = 焦距（像素为单位）— Apple 标定好的
- `d` = 该像素的深度值（米）— LiDAR 测的

直觉：`(bx - cx) / fx` 就是"这个像素偏离图像中心多少个焦距" = 光线的水平角度。乘以 `d` 就得到实际水平偏移量。

**第二步：相机坐标 → 世界坐标**

```swift
let camPoint = simd_float4(x_cam, y_cam, z_cam, 1.0)
let worldPoint = camera.transform * camPoint   // 4×4 矩阵乘法
```

`camera.transform` 是 ARKit 实时提供的 4×4 矩阵，包含：
- 旋转（手机朝哪个方向）
- 平移（手机在世界中的位置）

乘完之后，`worldPoint.xyz` 就是该点在**世界坐标系**中的绝对位置。

### 具体数值例子

```
假设：手机正前方 2m 处有个柱子，柱子稍微偏右
      手机在世界坐标 (0, 0, 0)，面朝 -Z

深度图像素 (bx=140, by=96)，深度 d=2.0m
相机内参：fx=180, fy=180, cx=128, cy=96

第一步：
  x_cam =  2.0 × (140 - 128) / 180 =  2.0 × 0.067 = +0.133m（右偏 13cm）
  y_cam = -2.0 × (96 - 96) / 180   =  0（同一高度）
  z_cam = -2.0m（前方 2m）

第二步（手机面朝 -Z，无旋转时 transform ≈ 单位矩阵）：
  worldPoint = (0.133, 0, -2.0)
  含义：世界中的位置 = 右边 0.133m，前方 2.0m
```

## 问题 2：我们以 5Hz 重建绝对世界坐标轴吗？

**不是"重建坐标轴"，是在同一个坐标轴下重新计算所有点的位置。**

关键区别：

| 概念 | 说明 |
|------|------|
| **世界坐标轴** | ARKit 在 `session.run()` 时建立，**一次性**，之后永远不变。原点 = 启动时手机位置 |
| **camera.transform** | 每帧 ARKit 实时更新（60Hz），告诉你"手机现在在世界坐标系中的位姿" |
| **我们每 0.2s 做的** | 用当前帧的深度图 + 当前帧的 transform，计算这一刻所有点的世界坐标 |

```
T=0.0s  ARKit建立世界坐标系，原点=(0,0,0)=启动位置
         ↓ 坐标轴从此固定，永不改变

T=0.2s  手机已走到 (0.3, 0, -0.3) → transform 更新
         我们用新 transform + 新深度图 → 192×192 个新世界坐标点
         （这些点在同一个坐标系下，只是反映了"此刻环境长什么样"）

T=0.4s  手机又走到 (0.5, 0, -0.6) → transform 又更新
         再次计算 192×192 个新点
         ...
```

**所以：**
- 坐标轴不重建（永远是 T=0 时的那个）
- 点云每 0.2s 全部重新算一遍（因为手机在动，深度图也在变）
- 我们**不保留历史点云** — 每次只用当前帧的数据

### 为什么不保留历史点云做累积？

1. **手机在动** — 0.2s 后同一个障碍物在深度图中的位置变了
2. **VIO 漂移** — 长期累积的点云会越来越不准
3. **简单高效** — 每帧独立分析 = 无状态累积、无内存增长、无旧数据污染

代价是：障碍物被短暂遮挡后立即"消失"（没有记忆）。

## 问题 3：时间平滑"拖影"怎么解决？

### 什么是拖影？

`smoothedSceneDepth` 是 Apple 对多帧深度进行时间平滑后的结果。当一个物体快速移动时：

```
T=0:  行人在 A 位置 → 深度图记录 A 的深度
T=1:  行人移到 B 位置 → 深度图应该更新
      但 smoothedSceneDepth 把 T=0 的数据混入了 → 
      A 位置残留一个"幽灵"（拖影）

深度图可能长这样：
  [A 位置: 深度=2.5m (残留)] [中间: 模糊] [B 位置: 深度=2.0m (真实)]
```

### 当前状态：我们没有专门解决拖影

坦白说，**目前代码里没有针对拖影的处理**。这是一个已知的局限（已记录在 Problems_and_Improvements 中）。

### 为什么现在影响不大？

1. **行人走动速度 ~1.4m/s**，0.2s 内移动 ~28cm。`smoothedSceneDepth` 的时间窗口约 2-3 帧（~50ms），50ms 内移动 ~7cm。拖影只有 **7cm 宽**，对 0.8m 通道宽度判定影响很小。
2. 我们的 **置信度过滤** 会拒绝部分拖影区域（深度不连续处置信度降低）
3. **滞后机制**（boolHysteresisOn=3 帧）本身就是一种时间过滤 — 一帧的拖影不足以改变输出

### 如果未来要解决，有三种方案：

| 方案 | 做法 | 代价 |
|------|------|------|
| **A. 用 `sceneDepth` 代替 `smoothedSceneDepth`** | 去掉时间平滑，每帧都是纯粹的当前测量 | 噪声增大（尤其远距离），需要我们自己做空间滤波 |
| **B. 运动检测 + 自适应** | 比较相邻帧深度图，检测哪些区域有大变化（＝有东西在动）→ 对这些区域用当前帧数据，其他区域用平滑数据 | 计算量增加，需要缓存上一帧深度图 |
| **C. 多帧点云对比** | 保留最近 2-3 帧的 worldPoints，找出不一致的点（消失/出现的点 = 动态物体）→ 标记为动态 | 内存翻倍，需要点对应算法 |

### 建议

**现阶段不需要解决**。理由：
- 我们的用户以步行速度移动（~1.4m/s）
- 环境中的动态障碍（其他行人）也是步行速度
- 7cm 拖影对 2.0m 安全距离判定影响 <4%
- 更紧迫的问题是仲裁层和端到端测试

**如果未来真机测试发现拖影导致了实际问题**（比如快速骑自行车的人产生的幽灵障碍导致急停），再用方案 B 解决。
