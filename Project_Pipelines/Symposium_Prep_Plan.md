## 问题优先级 & 解决顺序

### Phase 1: 硬件能跑（1-2 天）

#### Task 1.1 — ESP32 电池供电 + MOSFET 驱动
- **问题**：GPIO 40mA 不够驱动振动电机（需 60-100mA）
- **解决**：每个电机加 N-channel MOSFET（AO3400 或 2N7002）
- **采购**：3× MOSFET + 3× 10kΩ 下拉电阻
- **接线**：
  ```
  VBAT (3.7V) → 电机正极 → 电机负极 → MOSFET Drain
  GPIO → MOSFET Gate (+ 10kΩ 下拉到 GND)
  MOSFET Source → GND
  ```
- **验证**：电池供电下 3 个电机独立可控
- ⏱️ 预计：2-3 小时（含焊接）

#### Task 1.2 — ESP32 4 字节 BLE 协议
- **问题**：当前 2 字节 `[direction, magnitude]` 不能分别控制 3 个电机
- **解决**：升级为 `[cmd, L_intensity, F_intensity, R_intensity]`
  - ESP32 端：修改 BLE characteristic 解析
  - iOS 端：修改 `BLEManager.swift` 发送逻辑
- **验证**：iOS 发 `[0x01, 128, 0, 255]` → 左电机中等、前电机关、右电机全开
- ⏱️ 预计：2-3 小时

### Phase 2: 软件优化（2-3 天）

#### Task 2.1 — 拖影问题（方案 A：最快实现）
- **问题**：`smoothedSceneDepth` 对移动物体产生拖影
- **解决**：

  2. 加 3×3 中值滤波抑制单帧噪声
- **改动**：LiDARManager.swift ~30 行
- **验证**：对着走动的人，深度图无残影
- ⏱️ 预计：1 小时

#### Task 2.2 — 移动物体预警（方案 B：速度估计）
- **问题**：无法预测接近中的障碍物
- **解决**：比较相邻帧 `freeDistance[]` 变化率
  ```
  deltaRate = (freeDistance_prev[col] - freeDistance_curr[col]) / 0.2s
  if deltaRate > 1.0 m/s:  // 障碍物以 >1m/s 接近
    提前 1 级报警 (P2→P1, P1→P0)
  ```
- **改动**：LiDARManager.swift ~40 行（缓存上一帧 freeDistance + 比较）
- **验证**：人快速走向手机时，提前 0.4s 触发更高报警
- ⏱️ 预计：2 小时

#### Task 2.3 — 黑色物体空洞检测
- **问题**：黑色物体吸收红外光 → 深度图出现无效区域
- **解决**：检测 `validMask` 中被有效点包围的无效区域（空洞）→ 标记为潜在障碍
  ```
  如果一片 ≥5 列的连续区域全部 invalid，
  且左右两侧有效点距离 < 3m → 该区域可能是黑色障碍物
  ```
- **改动**：~50 行，在 `computeFreeSpaceMap` 后新增检测
- **验证**：对着黑色柱子/黑色墙壁测试
- ⏱️ 预计：2 小时

## VIO 漂移详细说明

### 漂移对当前系统的影响

VIO 漂移 = 世界坐标的原点慢慢"飘移"。但我们的核心计算都是**相对于当前相机位置**的：

```swift
let dx = pt.x - cameraPos.x  // 相对距离，不受漂移影响
let dz = pt.z - cameraPos.z  // 同上
let hdist = sqrt(dx*dx + dz*dz)
```

| 计算 | 用绝对坐标？ | 受漂移影响？ |
|------|-------------|-------------|
| 障碍物距离 | ❌ 用 pt - cameraPos | 不受 |
| 高度分类 | ❌ 用 pt.y - groundY | 不受（groundY 也漂移，差值不变）|
| 台阶检测 | ❌ 用相邻点 Y 差 | 不受 |
| 坡道检测 | ❌ 用线性回归斜率 | 不受 |
| 自由空间 | ❌ 用 pt - cameraPos | 不受 |

**结论**：VIO 漂移对 B2 管线**几乎无影响**。唯一理论风险是 `groundY` EMA 在极长时间后（>30 分钟）可能偏移，但 EMA 自身会持续校正。

**对宏观导航的影响**：我们用 GPS（不是 VIO）做路线跟踪，所以宏观导航也不受 VIO 漂移影响。

### 如果将来要做 VIO + GPS 融合

那时才需要认真处理漂移。方案：
- ARKit 的 `ARGeoTrackingConfiguration`（如果地区支持）
- 或自己做 GPS 锚点校正：每次 GPS 更新时，记录 VIO 位置 vs GPS 位置的偏差

## 移动物体详细说明

### 当前行为

每帧独立 → 能检测到移动物体的**当前位置**，但不知道它在移动。

```
T=0.0s: 行人距 4m → P5（安全）     — 实际：行人以 1.5m/s 朝你走来
T=0.2s: 行人距 3.7m → P5（安全）
T=0.4s: 行人距 3.4m → P5（安全）
T=0.6s: 行人距 3.1m → P5（安全）
T=0.8s: 行人距 2.8m → P4（侧面感知）  ← 首次有反馈，已过 0.8s
T=1.0s: 行人距 2.5m → P2（引导）
T=1.2s: 行人距 2.2m → P2
T=1.4s: 行人距 1.9m → P1
T=1.6s: 行人距 1.6m → P0（紧急停止）  ← 从首次反馈到 P0 = 0.8s
```

### 加入速度估计后（Task 2.2）

```
T=0.0s: 行人距 4m → P5
T=0.2s: 行人距 3.7m → deltaRate = 1.5m/s → ⚠️ 提前一级 → P4
T=0.4s: 行人距 3.4m → deltaRate = 1.5m/s → ⚠️ → P2（提前 0.4s）
...
```

提前 ~0.4s 预警 = 步行场景下多出 ~0.6m 的反应距离。
