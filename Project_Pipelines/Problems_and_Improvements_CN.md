## 2. 现存已知问题

### Issue #14 — `maxIndex` 可能跳过中间路段

- **位置**：`ViewController.checkUserThresholds()`（宏观导航）
- **问题**：当 `threshold_1_radius` 较大（4m）时，用户可能同时处于多个阈值1圆内。代码取 `maxIndex`（最远匹配点），可能跳过中间路段。
- **影响**：当前 r=4m 时影响较小。如果半径增大或路径点间距缩小，问题会加剧。
- **改进方案**：改用**距用户最近**的匹配点，或追踪"上一个确认的路径点"并只允许顺序推进。

## 3. LiDAR B2 管线 — 设计局限与改进方案

### 3.1 地面 Y 估计

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **直方图最低30%假设** | `histogramGroundY()` 在最低 30% Y 值区间找峰值。站在高台（舞台、天桥）上时，最低 30% 是下方空气，地面峰值在中间区域 | 改用**全局最大峰值**，或检测双峰分布 |
| **固定 bin 大小** | `binSize = 0.05m` — 对精度来说太粗，对噪声数据来说太细 | 根据数据分布范围自适应调整 bin 大小 |
| **距离段边界固定** | `[0, 1.5, 3.0, 5.0]m` 硬编码 — 不一定适合所有场景 | 根据点密度自适应调整段边界 |
| **EMA 在高程变化时滞后** | 上下台阶时 `groundYAlpha=0.1` 意味着约 10 帧才能收敛到新地面 | 检测到垂直速度时加快 alpha；或在确认台阶/坡道后触发事件重置 |
| **不支持多平面** | 每段假设只有一个地面平面 — 在路沿、错层区域会出错 | 用 RANSAC 或多峰直方图检测每段 2+ 个地面平面 |

### 3.2 点分类（Step C）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **仅基于高度分类** | 所有分类只看 `pt.y - groundY`，无形状、纹理、上下文信息 | 增加空间聚类 — 孤立高点可能是噪声，密集簇才是真实障碍 |
| **固定阈值** | `groundTolerance=0.08m`、`tripHazardHeight=0.15m` 等全局统一 | 按距离自适应调整阈值（远处深度噪声更大） |
| **无"头顶"分类** | 头顶上方物体（树枝、标牌）被分类为 `obstacleHigh`，但并非行走障碍 | 新增头顶分类：`h > 用户身高` → 从阻塞路径中排除 |
| **绊倒风险区间太窄** | 0.08–0.15m 范围仅 7cm — 噪声数据中容易遗漏 | 扩大区间或专门为绊倒检测添加滞后机制 |

### 3.3 台阶检测（Step E）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **仅扫描中央 ±10°** | 斜向接近台阶时可能漏检 | 扩大扫描范围，或沿检测到的安全路径方向扫描 |
| **无台阶数量输出** | 只返回 `Bool` — 不知道有几级台阶、总高差多少 | 返回台阶数 + 总高程变化，用于更精细的触觉反馈 |
| **易被遮挡干扰** | 有人站在台阶上时阶梯模式被破坏 | 多帧累积台阶证据 |
| **无法区分路沿和台阶** | 单级台阶（路沿）不触发检测（需 ≥3 级），但路沿仍然重要 | 增加单独的路沿检测（1-2 级阶梯模式，不同阈值） |

### 3.4 坡道检测（Step F）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **仅线性回归** | 假设坡道是直线 — 弯曲坡道或起伏地形无法处理 | 分段回归或多项式拟合 |
| **无坡度数值输出** | 只返回 `Bool`（上坡/下坡）— 不知道有多陡 | 返回坡度角（°），用于按比例调整触觉强度 |
| **中央 ±5° 范围太窄** | 斜向走向坡道时可能漏检 | 沿行走方向（GPS航向或安全路径角度）扫描 |

### 3.5 自由空间图（Step G）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **仅计算阻塞性障碍** | `tripHazard` 和 `dropMild` 不被视为阻塞 — 用户在 P4/P5 下可能走入绊倒区域 | 增加第二层"注意距离"图，包含绊倒风险 |
| **每列仅取最近距离** | 无法区分墙壁（整列阻塞）和悬浮障碍（部分阻塞） | 追踪每列阻塞的垂直范围 |
| **无时间持续性** | 每帧重新计算 — 短暂被遮挡的障碍物瞬间消失 | 维护短期占用记忆（最近 N 帧） |

### 3.6 安全路径寻找（Step H）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **固定 `safeWidthConstant=0.8m`** | 不考虑用户背包、轮椅等情况 | 用户可配置的宽度参数 |
| **固定 `minSafeDistance=2.0m`** | 在狭窄走廊中过于保守，在开阔地带又不够 | 自适应：检测到狭窄环境时缩短，户外增长 |
| **无路径轨迹规划** | 只选当前帧最优走廊 — 不考虑用户已经在往哪个方向走 | 考虑用户航向/惯性：优先选与当前行走方向一致的走廊 |
| **阻塞时的 best-effort 角度** | `noSafePathFound` 时返回最宽缝隙角度，即使该缝隙太窄 — 用户可能尝试挤过去 | 区分"停下来重新评估"和"可以尝试窄缝通过" |
| **前方锥体 ±15° 固定** | P0 判定使用硬编码 ±15° — 可能与实际行走方向偏差较大 | 使用罗盘/GPS 航向确定实际前方方向 |

### 3.7 时序平滑（Step I）

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **滞后参数全局统一** | `boolHysteresisOn=3` / `boolHysteresisOff=5` 对所有 flag 相同 — 台阶检测可能需要和安全路径不同的时序 | 每个 flag 单独设置滞后阈值 |
| **EMA 角度可能过冲** | 安全路径快速左右切换时，EMA 滞后于实际值 | 增加死区：当原始角度翻转符号时，重置 EMA 而非平滑穿越零点 |
| **非对称 EMA 仅覆盖一个变量** | `nearestObstacleDistance` 有快接近/慢远离 EMA，但 P0 关键的 `nearestForwardDistance` 没有 | 对 `forwardNearDist` 也应用非对称 EMA — 对 P0 响应速度至关重要 |

## 4. 宏观导航 — 局限与改进

| 局限 | 详情 | 改进方案 |
|------|------|----------|
| **GPS 精度 ~3-5m** | 城市峡谷中 GPS 漂移可达 10m+ — 导致虚假偏航判定 | 融合 ARKit VIO 位置（LiDAR 会话已提供）以提升局部精度 |
| **1 秒重规划延迟** | 偏航 → 等 1 秒 → 重规划。快速移动时可能太慢；GPS 噪声环境下可能太快 | 自适应延迟：根据置信度缩放（更多 GPS 样本确认偏航 → 更快重规划） |
| **无室内导航** | Google Maps Directions API 仅支持户外；无室内路点导航 | 增加室内模式：用 ARKit 锚点或 BLE 信标定位 |
| **航向仅靠罗盘** | 手机罗盘噪声 ±5-10°，且受磁场干扰 | 融合罗盘与 ARKit 相机航向，获得更稳定的方向 |
| **2 字节 BLE 协议** | 当前 `[direction, magnitude]` 无法分别发送 L/F/R 电机强度 | 升级为 4 字节 `[cmd, L, F, R]` — **已规划** |

## 5. 系统级 — 缺失组件

| 组件 | 状态 | 描述 |
|------|------|------|
| **仲裁层** | 🔲 未开始 | 融合宏观导航（Google Maps 方向）+ 微观导航（LiDAR P0-P5）为统一触觉指令。例：Google 说"右转"但 LiDAR 看到右边有墙 → 用 LiDAR 覆盖 |
| **ESP32 3 电机 PWM** | 🔲 未开始 | 接收 `[cmd, L, F, R]` BLE 数据 → 以独立 PWM 强度驱动 3 个电机 |
| **动态障碍物处理** | 🔲 未开始 | 迎面走来的行人 — 当前系统逐帧独立分析，无速度估计 |
| **用户速度自适应** | 🔲 未开始 | 走得快 → 需要更远检测距离和更早预警；站定 → 降低灵敏度 |
| **电池/热量管理** | 🔲 未开始 | 192×192 @ 5Hz 对 GPU 负载较大 — 无手机过热时的自适应降频 |
| **音频反馈通道** | 🔲 未开始 | 仅靠触觉可能无法传达台阶/坡道/落差类型 — 考虑骨传导音频补充 |
| **端到端真机测试** | 🔲 未开始 | 所有组件单独存在但从未联合测试 |

## 6. 性能顾虑

| 顾虑 | 当前状态 | 风险 | 缓解方案 |
|------|----------|------|----------|
| **手机过热** | 192×192 × 5Hz = 每秒 184K 点 + 完整 B2 管线 | 中等 — iPhone 12 Pro 持续 ARKit 10-15 分钟后可能降频 | 自适应分辨率：热状态为 `.serious` 时降至 96×96 |
| **内存波动** | `worldPoints` = 192×192 × 12 字节 ≈ 430KB/帧，每次新建 | 低 — 短生命周期，但 GC 压力累积 | 预分配缓冲区复用，而非每帧创建新数组 |
| **主线程阻塞** | `updateDepthGridUI` 以 5Hz 更新 256 个 UILabel | 中低 — 256 个 label 更新可能造成微卡顿 | 改用单个 `CALayer`/`UIImage` 渲染代替 256 个独立 label |
| **BLE 吞吐** | 2 字节 @ 5Hz = 微不足道 | 当前无 | 4 字节升级仍然微不足道；但如果后续传输障碍物列表数据，可能需要 MTU 协商 |

## 7. 优先级排序

### 高优先级（阻碍实际使用）
1. **仲裁层** — 没有它，宏观和微观导航可能相互冲突
2. **ESP32 4 字节协议 + 3 电机 PWM** — 硬件原型已有，需要固件
3. **端到端测试** — 所有组件已独立完成，但从未联合测试

### 中优先级（提升精度/鲁棒性）
4. 地面 Y 估计改进（多平面、台阶时更快收敛）
5. 自由空间时间持续性（跨帧障碍物记忆）
6. `forwardNearDist` 非对称 EMA（P0 响应速度）
7. 绊倒风险纳入注意距离图
8. 头顶障碍物过滤

### 低优先级（锦上添花 / 未来方向）
9. 自适应 `minSafeDistance` 和 `safeWidthConstant`
10. ARKit VIO + GPS 融合定位
11. 动态障碍物速度估计
12. 自适应热降频
13. 音频反馈通道
14. 室内导航支持
